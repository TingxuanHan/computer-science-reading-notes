# 【计算机程序设计艺术 TAOCP】卷3·6.1 顺序查找：从逐项比较，到把常用记录放在前面

设想一张很短的联系人表。我们知道要找谁，却不知道他在第几行。最直接的办法是从头往后看，直到找到名字，或者把整张表看完。这个过程简单得几乎没有设计空间，但只要问一句“每个名字被查找的机会一样吗”，问题就发生了变化。

第六章从顺序查找开始，先把一次查找究竟花在哪里说清楚。之后的二分查找、树、数字查找和散列，都在利用额外信息减少需要检查的部分。本篇关心三个层次：扫描循环怎样写、记录怎样排、访问之后是否调整次序。

> 阅读定位：《计算机程序设计艺术》第 3 卷《排序与查找》第 2 版，苏运霖译，国防工业出版社，2002 年；原书 §6.1，书内第 369—380 页。第六章引言见第 366—369 页。扫描 PDF 页码为书页加 13；第 380 页同时包含相邻小节。本文例子与 Python 程序为自拟。

## 1. 先分清成功查找和失败查找

表中有 $n$ 个互异的键码。一次“键码比较”指检查当前键是否等于目标，不把循环边界判断算进去。

若目标在第 $i$ 个位置，就做 $i$ 次比较。如果一次成功查找等概率地命中这 $n$ 个位置，那么

$$
E[C\mid\text{成功}]
=\frac{1+2+\cdots+n}{n}
=\frac{n+1}{2}.
$$

失败查找必须检查全部记录，因此

$$
C_{\text{失败}}=n.
$$

这两个数回答的是不同的问题。若成功概率为 $s$，且成功时各位置等概率，完整的均值才是

$$
E[C]=s\frac{n+1}{2}+(1-s)n.
$$

把“平均扫描一半”直接套在一个大量查无此项的系统上，会低估工作量。表允许重复键时，若要求返回第一个匹配项，命中位置的分布也不再自动均匀；若要求找齐全部匹配项，扫描通常要继续到末尾。

本节的线性时间结论还隐含了单位比较成本。比较两个长字符串可能检查多个字符；记录存放在顺序介质中时，走过一条记录的代价也可能依赖它的长度。

## 2. 哨兵省掉的是循环中的边界检查

普通循环每一轮要回答两件事：有没有越界，当前键是不是目标。哨兵法在表尾额外放一个目标键，于是循环一定会遇到匹配，可以把越界检查移到循环结束之后。

对原来的 $n$ 条记录来说：

- 在真实位置命中，键码比较次数仍是该位置的序号。
- 真实记录中不存在目标，会比较到第 $n+1$ 个位置，即哨兵。
- 返回结果前必须判断停下的位置是不是哨兵，不能把人为补上的元素当成查找成功。

因此，哨兵法没有把最坏复杂度从 $O(n)$ 变成更小的阶。它改变的是循环内部的操作组合。原书在具体机器模型中分析这样的常数差异；在 Python 中，复制列表、解释器开销和内置函数实现都可能改变实际表现，不能仅凭少写一个条件就断言更快。

有序表还提供了另一种停止依据。若按升序扫描，并且当前键已经大于目标，就可以提前报告失败。这个依据来自顺序关系，不来自哨兵。维护顺序需要成本，成功查找也未必因此少看很多项。

## 3. 访问概率不同，应该怎样排

先只考虑成功查找。记录 $i$ 被访问的概率为 $p_i$，满足

$$
p_i\ge 0,\qquad \sum_i p_i=1.
$$

若顺序为 $\pi(1),\ldots,\pi(n)$，期望比较次数就是

```math
C(\pi)=\sum_{r=1}^{n}r\,p_{\pi(r)}.
```

为什么应当让高概率记录靠前？考察相邻的两条记录 $A,B$，它们位于第 $r,r+1$ 个位置。两种排列的差是

$$
[rp_A+(r+1)p_B]-[rp_B+(r+1)p_A]
=p_B-p_A.
$$

只要 $p_A<p_B$，把 $B$ 换到前面就会降低期望成本。不断消除这样的相邻逆序，得到按访问概率非增排列的最优静态次序。概率相等的记录可以任意交换。

自拟例子中，三条记录的概率为

$$
(p_A,p_B,p_C)=\left(\frac12,\frac13,\frac16\right).
$$

按 $A,B,C$ 排列，期望比较次数是 $5/3$；反过来排则是 $7/3$。记录条数没变，平均成本已经不同。

概率分布也会改变规模增长的含义。例如，若 $p_i=1/(iH_n)$，其中 $H_n=\sum_{i=1}^n1/i$，并按这个次序存储，那么

$$
C=\sum_{i=1}^n i\frac{1}{iH_n}
=\frac{n}{H_n}.
$$

这只是指定分布下的结论，不能把某个现实业务随意认作这个模型。真正值得保留的是计算方法：把位置成本乘上访问概率，再相加。

## 4. 不知道概率时，让访问过程调整表

实际访问频率可能未知，也可能随时间变化。原书讨论的自组织办法包括：

| 规则 | 成功访问后做什么 | 直观效果 |
| --- | --- | --- |
| 移到表头，move-to-front | 把命中的记录移到第一个位置 | 很快响应最近出现的热点 |
| 与前项交换，transpose | 只向前移动一格 | 调整温和，形成稳定顺序较慢 |

移到表头并不保证每一次都比静态最优次序好。一个很少访问的项目突然出现，也会暂时把热门记录挤向后面。它的价值是不用预先知道概率，并且能够响应时间局部性。

在独立同分布请求、所有 $p_i>0$、运行足够久达到稳态的模型中，可以精确分析移到表头。两条记录 $i,j$ 谁在前面，取决于它们中谁最近被访问过。因此

$$
P(j\text{ 在 }i\text{ 前面})=\frac{p_j}{p_i+p_j}.
$$

访问 $i$ 的比较次数等于 1 加上它前面的记录数。对所有记录求期望，再把有序对合成无序对：

```math
C_{\mathrm{MTF}}
=1+2\sum_{i\lt j}\frac{p_ip_j}{p_i+p_j}.
```

如果已经按 $p_1\ge p_2\ge\cdots\ge p_n$ 编号，那么每一项满足

```math
\frac{p_ip_j}{p_i+p_j}\le p_j\quad(i\lt j).
```

从而得到一个容易验证的界：

$$
C_{\mathrm{MTF}}
\le 1+2\sum_{j=1}^{n}(j-1)p_j
=2C_{\mathrm{opt}}-1.
$$

这个结论说的是特定随机模型中的稳态**查找比较次数**。它没有计入 Python 列表搬移元素的时间，也不是任意请求序列上的逐次保证。若访问存在突发热点，独立请求模型本身就需要重新审视。

## 5. 记录长度不同，按概率排序可能不再最优

现在假设必须从头读过记录，读取长度为 $L_i$ 的记录需要成比例的时间，并且要读完命中的记录。顺序 $\pi$ 的期望读取量为

$$
B(\pi)=\sum_{r=1}^{n}p_{\pi(r)}
\left(\sum_{t=1}^{r}L_{\pi(t)}\right).
$$

相邻的 $A,B$ 换位，不会改变更早或更晚记录的成本。只比较这两条记录，得到

$$
B(AB)-B(BA)=p_BL_A-p_AL_B.
$$

因此 $A$ 放在 $B$ 前面的条件是

$$
\frac{p_A}{L_A}\ge\frac{p_B}{L_B}.
$$

应按“访问概率除以记录长度”非增排列。一个很长的热门记录，可能应该放在一个短而次热门的记录后面。

沿用前面的三个概率，再令长度为 $(5,1,2)$。按概率排是 $A,B,C$，期望读取量 $35/6$；按比值排是 $B,A,C$，期望读取量降到 $14/3$。这是顺序读取成本模型的结论。若通过指针随机访问，或者只读取固定长度键码，成本函数就不一样。

## 6. 可运行的比较计数与顺序实验

下面使用整数键；成功返回第一个匹配下标，失败返回 $-1$。哨兵版本为了保持调用方列表不变而复制输入，复制需要额外 $O(n)$ 时间和空间，但不计入返回的“键码比较次数”。这段代码用于核对计数，不用于证明 Python 运行速度。

```python
from fractions import Fraction as F


def linear_find(a, key):
    for i, value in enumerate(a):
        if value == key:
            return i, i + 1
    return -1, len(a)


def sentinel_find(a, key):
    work = list(a) + [key]
    i = 0
    while work[i] != key:
        i += 1
    return (i if i < len(a) else -1), i + 1


def move_to_front(a, key):
    i, comparisons = linear_find(a, key)
    if i >= 0:
        a.insert(0, a.pop(i))
    return comparisons, i >= 0


def expected_cost(order, probabilities, lengths=None):
    prefix = 0
    cost = F(0)
    for key in order:
        prefix += 1 if lengths is None else lengths[key]
        cost += probabilities[key] * prefix
    return cost


p = {"A": F(1, 2), "B": F(1, 3), "C": F(1, 6)}
length = {"A": 5, "B": 1, "C": 2}
by_probability = sorted(p, key=p.get, reverse=True)
by_ratio = sorted(p, key=lambda k: p[k] / length[k], reverse=True)

print(linear_find([4, 7, 9], 8), sentinel_find([4, 7, 9], 8))
print(expected_cost(by_probability, p), expected_cost("CBA", p))
print(by_ratio, expected_cost("ABC", p, length),
      expected_cost(by_ratio, p, length))
a = [4, 7, 9]
print(move_to_front(a, 7), a)
```

输出：

```text
(-1, 3) (-1, 4)
5/3 7/3
['B', 'A', 'C'] 35/6 14/3
(2, True) [7, 4, 9]
```

可以进一步枚举三条记录的全部排列，分别比较两种成本函数的最小值。再将查找输入换成空表、包含重复项的表、首项命中、末项命中和完全缺失，检查返回位置与比较次数是否一致。

## 7. 读完这一节，再看查找算法的评价

顺序查找适合数据少、建索引不划算、数据只能顺序到达，或者访问高度集中于前面少量记录的场景。它也能成为检验复杂结构的基准：无论索引怎样组织，最终结果都应当与朴素扫描一致。

这一节值得反复使用的分析顺序是：先写清成功与失败的含义，再确定成本单位，最后加入概率和调整规则。只写一个 $O(n)$，会丢掉前面这些差别；只看一次运行时间，又可能把输入分布和实现细节混在一起。
