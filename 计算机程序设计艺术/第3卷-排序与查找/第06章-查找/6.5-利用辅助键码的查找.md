# 【计算机程序设计艺术 TAOCP】卷3·6.5 利用辅助键码的查找：从一条记录，走向一组条件

前几节常把查找描述成“给定键，找到对应记录”。现在换一种请求：找出地区为东部、使用 Python、年份不早于 2024 的全部项目。

一个条件可能命中许多记录，一条记录也可能满足许多条件。查询结果可以为空，也可以占据大半张表。§6.5 讨论的辅助键码查找，正是怎样为这些条件组织信息，以及怎样把若干条件的结果组合起来。

> 阅读定位：《计算机程序设计艺术》第 3 卷《排序与查找》第 2 版，苏运霖译，国防工业出版社，2002 年；原书 §6.5，书内第 521—543 页，扫描 PDF 页码为书页加 13。第 544 页开始习题答案。本篇用自拟记录说明倒排表、位图和叠加编码，并结合原书讨论多维检索与组合组织。

## 1. 查询条件先写成集合

设当前有效记录的标识集合为 $U$。对一个属性条件 $A$，记满足条件的记录集合为 $S_A$，则

$$
S_{A\land B}=S_A\cap S_B,\qquad
S_{A\lor B}=S_A\cup S_B,
$$

$$
S_{\lnot A}=U\setminus S_A.
$$

这里的 $U$ 不能省略。若已经删除部分记录，取反时仍把历史编号都当成有效记录，就可能返回不存在的结果。

辅助键码通常不唯一。例如，多条记录都可以属于“东部”。索引的键也应包含字段名：“地区=东部”与“来源=东部”是两个不同的条件，不能因为值相同就混在一起。

本文采用明确的二值语义：一条记录满足某个等值条件，当且仅当该字段存在且值相等；该条件的补集包含所有不满足的有效记录。这不是对某种数据库空值逻辑的模拟。

如果只查询一次，扫描原表可能已经足够。建立索引需要时间和空间，修改记录又要维护索引；先估计查询次数和更新方式，比先决定使用哪种数据结构更合理。

## 2. 倒排表：从属性值走向记录标识

原始表按记录组织：给一个记录标识，可以读出所有字段。倒排表把方向倒过来：

```math
(\text{字段},\text{值})\longmapsto
\{\text{具有该属性值的记录标识}\}.
```

例如，自拟数据中的“语言=Python”对应 $`\{0,1,3\}`$，“地区=东部”对应 $`\{0,2,3\}`$，交集就是 $`\{0,3\}`$。

若倒排列表按记录标识排序，可以用两个指针求交集。较小的标识向前走，相等时输出并同时前进；长度分别为 $a,b$ 时，合并式交集的时间上界是 $O(a+b)$。

多个 AND 条件常从较短的候选集开始，有机会很早把结果缩小到空集。这个策略依赖列表长度、成员查询方式与数据相关性，并不保证只凭长度就能选出全局最优计划。OR 查询要保留所有分支命中的记录，不能只检查最短的一张表。

索引中最好保存稳定的记录标识，或保存经维护的地址映射。若直接保存数组当前位置，原表插入、压缩或排序后，旧位置可能已经指向另一条记录。

删除和修改同样需要维护一致性。例如把一条记录的语言从 Python 改成 Rust，既要从旧倒排表移除它，也要加入新倒排表。只更新一边会分别产生漏报或多报。

## 3. 位图把集合操作变成按位操作

若记录编号适合映射到位位置，可以为每个条件建立位图 $B_A$：

$$
B_A[i]=1\iff i\in S_A.
$$

交、并分别对应按位 AND、OR。否定条件必须与有效记录位图 $B_U$ 一起使用：

```math
B_{\lnot A}=B_U\mathbin{\&}(\mathop{\sim} B_A).
```

这在 Python 中尤其容易出错：整数的按位取反不是“仅翻转当前显示的有限几位”。用有效记录掩码限制结果，才能避免得到带无限符号扩展含义的负整数。

位图并不意味着任意规模的查询只需常数时间。若位图有 $N$ 位，机器字宽为 $w$，逐字操作需要约 $O(N/w)$ 的工作；Python 大整数也会随内部字数增长。最终枚举命中的记录还要付出输出成本。

稀疏倒排列表按命中记录数占空间；未压缩位图按编号范围占空间。如果只有少数记录，但编号从 1 跳到十亿，直接以编号作为位位置会浪费很多空间，应先建立紧凑映射，或选择其他表示。

## 4. 多个字段如何一起组织

一种办法是按组合键排序，例如按

$$
(\text{地区},\text{语言},\text{年份})
$$

的字典序组织记录。固定地区、再固定语言时，满足条件的记录形成连续范围；只固定年份时，结果却可能分散在不同地区和语言的区段。

这解释了为什么字段顺序会影响查询。可以维护多个不同顺序的组合索引，覆盖更多查询模式，但会增加空间及更新费用。原书进一步用排列和组合构造研究：怎样用较少的属性顺序，让不同属性子集的查询都能找到连续片段。

另一种办法是把记录看作多维空间中的点。范围条件对应区域，四叉树、按维度分割的树等结构通过空间划分排除不可能命中的区域。树高平衡，并不意味着每个多维范围查询只访问一条根到叶子的路径；查询区域可能与许多分区相交。

原书还讨论广义检索结构：当前节点检查某个属性位，查询指定 0 或 1 时只走相应分支，指定“任意”时两边都要走。未指定属性越多，需要保留的候选区域通常越多。关于随机多维结构的平均公式，都有对应的分布和查询模型。

无论索引多巧，若最终需要返回 $k$ 条记录，就至少要做与 $k$ 成比例的输出工作。“快速定位”与“返回很多结果”要分开评价。

## 5. 叠加编码：可以快速排除，也可能误报

为每个属性 $a$ 分配一段位码 $c(a)$，把一条记录具有的属性集合 $R$ 编码成

$$
\sigma(R)=\bigvee_{a\in R}c(a).
$$

查询要求包含属性集合 $Q$ 时，若

```math
\sigma(R)\mathbin{\&}\sigma(Q)\ne\sigma(Q),
```

那么 $R$ 一定不包含全部要求的属性，可以立即排除。反过来，位码通过测试只说明“可能包含”，仍应读取原始属性确认。

自拟一个很小的例子：

$$
c(A)=001,\quad c(B)=010,\quad c(C)=011.
$$

查询同时包含 $A,B$ 时，查询位码为 011。只含 $C$ 的记录也得到 011，会通过位码检查，却不是真正答案。这就是误报。

在编码规则一致、索引完整且只作正向包含筛选的条件下，真正满足包含条件的记录不会被这个测试排除，因为按位 OR 不会丢掉已置为 1 的位。但不能把“可能包含”的结果直接取反来回答否定条件，否则误报会转化成漏掉真答案。

## 6. Bloom 过滤器把整个键集合压成一个位表

原书在叠加编码的讨论中介绍了 Bloom 的方法。为 $n$ 个键准备 $m$ 个比特，每个键通过 $k$ 个散列位置把相应位设成 1。查询时，只要其中一位为 0，就能确认不存在；全部为 1，则还要到实际记录结构中确认。

在各散列位置独立均匀的模型中，一位在插入后仍为 0 的概率为

$$
\left(1-\frac1m\right)^{kn}
\approx e^{-kn/m}.
$$

再把查询涉及的位近似视为独立，一个不存在键的误报率近似为

$$
f\approx(1-e^{-kn/m})^k.
$$

这不是有限位表的精确恒等式：位之间会有相关性，散列位置也可能重复。把 $k$ 暂时当成连续变量优化这个近似式，得到

$$
k_{\mathrm{opt}}\approx\frac mn\ln2.
$$

此时约一半的位被置为 1。例如每个键分配 10 位，选 $k=7$，模型预测的误报率约为 $`0.82\%`$。这是参数模型的计算结果，不是任何具体实现的实测承诺。

普通插入式 Bloom 过滤器不能在删除一个键时直接把它涉及的位全部清零，因为这些位可能同时被其他键使用。错误清零会产生假阴性。更复杂的删除方案需要额外计数或其他维护机制。

它的实用角色是先挡住大量确定不存在的请求，节约昂贵的后续访问。通过过滤器的请求仍然需要精确检查；它本身不返回完整记录。

## 7. 可运行的倒排、位图与候选确认

下面的索引针对一份静态数据快照建立。记录改变后应重新建立；示例没有宣称实现增量维护或并发事务。倒排部分使用 Python 集合，因此它的求交实现不同于前面分析的有序列表双指针法。

```python
def build_indexes(records):
    postings, bitmaps = {}, {}
    universe_bits = 0
    for rid, fields in records.items():
        if type(rid) is not int or rid < 0:
            raise ValueError("nonnegative integer record IDs required")
        universe_bits |= 1 << rid
        for field, value in fields.items():
            term = (field, value)
            postings.setdefault(term, set()).add(rid)
            bitmaps[term] = bitmaps.get(term, 0) | (1 << rid)
    return postings, bitmaps, universe_bits


def intersect(postings, terms, universe):
    result = set(universe)
    lists = sorted((postings.get(t, set()) for t in terms), key=len)
    for ids in lists:
        result.intersection_update(ids)
        if not result:
            break
    return result


def bitmap_query(bitmaps, positive, negative, universe_bits):
    result = universe_bits
    for term in positive:
        result &= bitmaps.get(term, 0)
    for term in negative:
        result &= ~bitmaps.get(term, 0)
    return result


def bit_ids(mask):
    if mask < 0:
        raise ValueError("finite nonnegative bitmap required")
    while mask:
        low = mask & -mask
        yield low.bit_length() - 1
        mask ^= low


def signature(attributes, codes):
    bits = 0
    for attribute in attributes:
        bits |= codes[attribute]
    return bits


def filter_then_confirm(documents, required, codes):
    required = set(required)
    query_bits = signature(required, codes)
    candidates = [
        rid for rid, attributes in documents.items()
        if signature(attributes, codes) & query_bits == query_bits
    ]
    confirmed = [rid for rid in candidates
                 if required <= documents[rid]]
    return sorted(candidates), sorted(confirmed)


records = {
    0: {"area": "east", "lang": "Python", "year": 2024},
    1: {"area": "west", "lang": "Python", "year": 2023},
    2: {"area": "east", "lang": "Rust", "year": 2024},
    3: {"area": "east", "lang": "Python", "year": 2025},
    4: {"area": "west", "lang": "Rust", "year": 2024},
}
postings, bitmaps, active = build_indexes(records)
terms = [("area", "east"), ("lang", "Python")]
print(sorted(intersect(postings, terms, records)))
print(list(bit_ids(bitmap_query(bitmaps, terms, [], active))))
print(list(bit_ids(bitmap_query(bitmaps, terms, [("year", 2025)], active))))
documents = {0: {"A", "B"}, 1: {"C"}, 2: {"A"}}
codes = {"A": 0b001, "B": 0b010, "C": 0b011}
print(filter_then_confirm(documents, {"A", "B"}, codes))
```

输出：

```text
[0, 3]
[0, 3]
[0]
([0, 1], [0])
```

前两行说明倒排交集与位图交集给出相同结果。加入年份否定条件后只剩记录 0。最后一行故意制造误报：记录 1 进入候选集，但读取真实属性后被排除，最终答案仍然准确。

验证时可以枚举小数据集上的条件组合，把索引结果与逐记录扫描比较；还要检查空条件、缺失属性值、空数据集，以及删除记录后更新有效记录集合的情况。对叠加编码则分别检查候选集包含全部真答案，以及确认后的结果恰好等于真答案。

## 8. 本节末尾的组合设计在解决什么

如果为每对属性都建立联合倒排表，查询方便，但同一记录会被重复列入许多表。原书以区组设计说明，怎样共享部分组合结构来降低这种冗余。

以 Steiner 三元系统为例，每对属性恰好出现在一个三元组中。若有 $v$ 个属性，每个三元组覆盖三对，所以三元组数必须是 $v(v-1)/6$；每个属性又应出现在 $(v-1)/2$ 个三元组中。整除条件要求

$$
v\equiv1\ \text{或}\ 3\pmod6.
$$

这样的计数解释了组合组织的限制，也说明索引设计可能遇到纯粹的组合问题。数学结构漂亮，并不自动意味着维护简单或性能最佳；仍需比较重复存储、查询步骤和更新工作。

本版章末对持久数据结构的文字是后续版本安排的说明，不能据此把它当作本版已经展开的 §6.6。至此，第六章的五个一级小节已读到章末。

整章的查找方式可以接成一条线：顺序扫描控制位置成本，比较查找排除有序区间，数字查找利用键的组成，散列计算候选地址，辅助键码查找组织多个条件。每一种方法都要说明何时成功、何时能安全失败，以及更新后这些判断为什么仍然成立。
