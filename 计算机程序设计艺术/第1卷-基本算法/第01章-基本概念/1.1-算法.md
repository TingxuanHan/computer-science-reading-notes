输入两个正整数，输出它们的最大公因子。这个问题用 Python 写起来只有几行，但代码短，并不意味着它已经被解释清楚。

我们仍然需要回答：两个数有没有大小要求？替换变量后为什么答案不变？循环为什么一定结束？“每一步都能执行”与“运行得足够快”又有什么区别？

§1.1 用这样一个小问题建立后续全书的表达习惯：先把计算过程写准确，再讨论它的正确性和代价。

## 1. 先给算法一个明确的问题

设输入为两个正整数 $m_0,n_0$，输出为

$$
d=\gcd(m_0,n_0).
$$

下标 0 用来保留原始输入。程序运行时的变量 $m,n$ 会变化，不能把它们在不同时间的值混为一谈。

这里的输入范围是正整数。关于零和负数的最大公因子也可以约定，但需要另行说明规则，不能让程序的偶然行为代替定义。

原书的算法 E 可以概括成三个动作：

1. 计算 $r=m\bmod n$，满足 $0\le r<n$。
2. 如果 $r=0$，返回 $n$。
3. 否则令 $m\leftarrow n$、$`n\leftarrow r`$，回到第一步。

例如输入 $252,105$，执行过程如下。

| 轮次 | $m$ | $n$ | $m=qn+r$ | 下一步 |
|---|---:|---:|---|---|
| 1 | 252 | 105 | $252=2\times105+42$ | 改为 $(105,42)$ |
| 2 | 105 | 42 | $105=2\times42+21$ | 改为 $(42,21)$ |
| 3 | 42 | 21 | $42=2\times21+0$ | 返回 21 |

不要求一开始就有 $m\ge n$。如果 $m<n$，第一轮余数就是 $m$，更新后两者交换位置。例如 $(105,252)$ 会先变为 $(252,105)$。预先交换可以省掉这一轮取余，但不是保证正确性所必需的步骤。

## 2. 赋值顺序本身就是算法的一部分

数学等式 $m=n$ 表示一个关系；赋值 $m\leftarrow n$ 表示用 $n$ 的当前值覆盖 $m$。

已经算好 $r$ 之后，下面两行可以正确推进算法：

```text
m ← n
n ← r
```

如果反过来写：

```text
n ← r
m ← n
```

两者最后都变成了原来的 $r$。以第一轮为例，状态会错误地变为 $(42,42)$，随后返回 42，而正确答案是 21。

程序里的变量是有时间顺序的存储位置。修改它之前，需要确认旧值是否还会被后面的动作使用。这也是后来学习数组原地修改、链表改链和排列循环时会反复遇到的问题。

## 3. 为什么替换后答案不变

由带余除法，有

$$
m=qn+r.
$$

如果正整数 $d$ 同时整除 $m,n$，它也整除

$$
r=m-qn.
$$

反过来，如果 $d$ 同时整除 $n,r$，它也整除

$$
m=qn+r.
$$

于是 $(m,n)$ 与 $(n,r)$ 的正公因子集合完全相同，当然也就有

$$
\gcd(m,n)=\gcd(n,r).
$$

这比观察几个样例得到相同结果更强：它说明每一次合法的更新都保持答案不变。循环过程中，我们始终保有关系

$$
\gcd(m,n)=\gcd(m_0,n_0).
$$

这个关系就是循环不变式。它不是“所有变量都不变”，而是变量变化时，一个足以说明问题的关系保持成立。

当算法发现 $r=0$ 时，$`n`$ 整除 $m$，所以此时的最大公因子就是 $n$。再结合不变式，返回值就是原始问题的答案。

## 4. 为什么一定会结束

上面的证明说明了“如果返回，就会返回正确答案”。还要证明它确实会返回。

只要算法继续执行，余数就满足

$$
0<r<n.
$$

更新之后，新的第二个变量等于这个 $r$。因此，在连续执行的各轮之间，第二个变量形成严格递减的正整数序列。

正整数不能无限下降，所以算法必然在有限轮之后遇到余数 0。

这里有两个各司其职的量：最大公因子关系保持不变，用来说明答案；第二个变量不断减小，用来说明终止。阅读一个循环时，把这两个问题分开，会比笼统地说“循环显然正确”清楚得多。

## 5. 原书列出的五个特征

把欧几里得算法放回原书的定义中，可以逐项检查。

| 特征 | 要求 | 在算法 E 中的对应 |
|---|---|---|
| 有限性 | 每个允许的输入都在有限步后结束 | 第二个变量严格下降 |
| 确定性 | 每一步的含义明确，没有执行上的歧义 | 正整数取余、零判断、赋值均有明确规则 |
| 输入 | 输入可以有零个或多个，并说明取值范围 | 两个正整数 |
| 输出 | 有与输入满足规定关系的输出 | 最大公因子 |
| 能行性 | 基本步骤原则上能精确、有限地完成 | 整数除法、比较和赋值可落实为基本操作 |

“有限性”并不要求所有输入共享同一个固定的步数上限。输入越大，允许需要越多步骤；要求的是每个给定的合法输入都能结束。

“能行性”也不能直接理解成“高效率”。一个需要天文数量步骤的过程，仍可能满足有限性和能行性。原书接着讨论算法分析，正是因为能算出答案以后，还要追问需要多少资源。

持续响应外部事件的服务程序可以有意义地一直运行。按本节围绕终止建立的概念，这类整体过程需要与解决一次有限输入问题的算法区别讨论；不能据此认定长期运行的程序没有价值。

## 6. 把说明落实到可运行代码

下面用更常见的 `while n != 0` 写法实现。它在最后一次取余后也更新变量，因此返回的是 $m$；原书算法 E 则在余数为零时直接返回当时的 $n$。两种写法的返回位置不同，状态关系一致。

```python
from math import gcd


def euclid_trace(m: int, n: int):
    """只接受 Python 正整数，返回 (最大公因子, 每轮状态)。"""
    if type(m) is not int or type(n) is not int:
        raise TypeError("m 和 n 必须是整数")
    if m <= 0 or n <= 0:
        raise ValueError("m 和 n 必须为正数")

    rows = []
    while n != 0:
        q, r = divmod(m, n)
        rows.append((m, n, q, r))
        m, n = n, r
    return m, rows


answer, rows = euclid_trace(252, 105)
print(answer)
print(rows)

for m in range(1, 129):
    for n in range(1, 129):
        answer, _ = euclid_trace(m, n)
        assert answer == gcd(m, n)
```

输出为：

```text
21
[(252, 105, 2, 42), (105, 42, 2, 21), (42, 21, 2, 0)]
```

Python 的同时赋值先求出右侧各项，再更新左侧变量。这里保留了整个执行轨迹，方便把代码与表格逐行核对。仅计算答案时可以去掉 `rows`；否则额外空间会随轮数增长，不能再说这个带追踪功能的实现只使用常数个存储槽。

上述检查覆盖 $128^2=16,384$ 对正整数，能发现实现中的一些错误。一般性的正确性依据仍是前面的公因子集合证明和终止证明。

## 7. 从轮数走向算法分析

对 $(252,105)$，取余执行 3 次；对 $(105,252)$，执行 4 次。即使答案相同，计算路径也不必相同。

一个直接的后续问题是：输入扩大之后，取余次数怎样增长？还可以把问题问得更细：一次取余是按固定代价计数，还是要按整数的位数计算？这两种成本模型会得到不同层次的复杂度说明。

因此，分析性能至少要明确输入规模、所数的操作、输入分布或最坏情况。只给出某次运行的毫秒数，还不能说明整个算法在一类输入上的行为。

原书 §1.1 已经提出对欧几里得算法的执行次数进行研究，但详细分析会走向后面的章节。本篇先把“算法描述—正确性—终止性—代价问题”这条线建立起来。
