# 【计算机程序设计艺术 TAOCP】卷1·1.4 某些基本程序设计技术：调用、协作与解释

> 对应原书：第 1 卷《基本算法》第 3 版，§1.4“某些基本程序设计技术”，书内第 178—221 页。涵盖子程序、共行程序、解释性程序、输入输出及历史文献。底本为苏运霖译、国防工业出版社 2002 年版。本文中的 Python 程序是另行设计的教学示例。

一个算法可以用几条步骤说清楚，完整程序却还要处理很多事情：一段代码会被多个位置调用；一个计算要暂停，等另一个计算提供数据；输入设备尚未完成，CPU 已经准备继续工作。

§1.4 讨论的正是这些组织方式。贯穿本节的问题是：**控制交给谁，恢复时从哪里继续，哪些状态需要保存？**

## 1. 子程序：把返回位置也作为状态

调用一个求最大值的子程序时，至少需要约定输入放在哪里、结果放在哪里、哪些寄存器会被改写，以及结束后回到哪条指令。

在 MIX 中，原书利用 `rJ` 保存与跳转有关的返回位置。典型形式可以概括为：

```text
调用处：跳转到子程序，同时记下返回位置
入口处：保存这个返回位置
执行子程序主体
出口处：跳回保存的位置
```

书中的具体实现会把返回地址写进出口跳转指令的地址字段。这涉及自修改代码，是理解该 MIX 程序时必须识别的机制。现代实现可以把返回地址保存在栈或其他专门位置；应理解的是状态保存需求，而不是机械搬用这一种保存方式。

### 为什么嵌套调用需要更多存储

假设 A 调用 B，B 再调用 C。进入 B 时要保留“回到 A 哪里”；进入 C 时又要保存“回到 B 哪里”。如果始终只使用同一个保存槽，第二次保存就会覆盖第一次。

这解释了调用栈为什么自然：每次活动调用都有自己的返回位置和局部状态，返回时按相反顺序取回。递归也是同样的问题，不能因为函数名相同，就让不同层的调用共享一份尚未使用完的状态。

### 接口需要说明副作用

对于一个寻找最大值的函数，只写“返回最大值”仍可能不够。下面这些约定会直接影响调用方：

| 项目 | 可以明确写出的约定 |
|---|---|
| 输入条件 | 数组非空，元素支持规定的比较 |
| 返回值 | 最大值及其位置 |
| 相等时的选择 | 返回最右侧最大值的位置 |
| 被修改的状态 | 是否修改原数组、哪些寄存器被覆盖 |
| 失败方式 | 空输入抛异常，或由调用方保证不出现 |

原书在介绍子程序时特别列出入口条件、出口条件和受影响的寄存器。高级语言隐藏了寄存器细节，但对可变参数、共享状态和异常行为，仍然需要同样清楚的说明。

## 2. 把重复代码抽出来，会付出什么代价

按原书讨论的简化 MIX 情形，假设长度为 $k$ 个存储单元的代码在 $m$ 个调用位置重复出现。

直接展开需要 $mk$ 个单元。如果改为子程序，每个调用处用一条跳转，主体保留一份，再加两条链接指令，所需单元数为

$$
k+m+2.
$$

节省量为

$$
mk-(k+m+2)=(m-1)(k-1)-3.
$$

例如 $k=10,m=5$，直接展开是 50 个单元，子程序形式是 17 个，节省 33 个。

这个模型暂未计入传参、保存寄存器和处理特殊情况的额外代码。若一个函数本来很小，或调用方式复杂，不能仅凭“复用”二字判断它一定更省空间、更快。子程序还提供了局部推理和独立调试的边界，这些价值需要与调用成本一起考虑。

## 3. 共行程序：保留上一次停下来的地方

本译本的“共行程序”对应 coroutine，本文同时使用常见译名“协程”。

普通子程序调用通常从入口开始，执行完成后返回。协程则可以在中途让出控制，下次恢复时从上次暂停的位置继续，并保留需要的局部状态。

原书强调协程之间可以具有对称关系：A 把控制交给 B，B 再交回 A，双方各自从上次暂停处恢复。这个概念本身不保证多个处理器同时执行，也不必依赖操作系统线程。

### 用一个数据管道观察暂停和恢复

假设数据按块到达，但一个整数可能跨越块边界：

```text
块 1："12 "
块 2："3 4"
块 3："5 -"
块 4："2"
```

正确解析出的整数是 `12, 3, 45, -2`。块末尾出现 `4` 时，还不能立即把它当作完整整数，因为下一块可能以 `5` 开始。

下面的生成器保留尚未结束的 token，并把整数逐个交给累计求和过程：

```python
def integers_from_chunks(chunks):
    token = ""
    for chunk in chunks:
        for ch in chunk:
            if ch.isspace():
                if token:
                    yield int(token)
                    token = ""
            else:
                token += ch
    if token:
        yield int(token)


def running_totals(values):
    total = 0
    for value in values:
        total += value
        yield total


chunks = ["12 ", "3 4", "5 -", "2"]
pipeline = running_totals(integers_from_chunks(chunks))
print(next(pipeline))
print(list(pipeline))
```

输出为：

```text
12
[15, 60, 58]
```

第一次 `next` 只推进到第一个累计值。再次请求时，两个生成器继续此前的循环，累计和、当前块的位置等状态得以保留。

这个例子用 Python 生成器展示挂起和恢复，属于调用方驱动的控制方式，不等同于原书对称协程的全部实现机制。它也没有启动后台读取或并行计算。

这里约定输入是由空白分隔的整数文本；非法 token 会由 `int` 报错。结束时必须处理最后一个没有尾随空白的 token。程序避免积攒整个输入，但仍需要保存一个 token；如果 token 很长，内存和字符串处理成本也会增长。

## 4. 解释程序：把指令当作输入数据

解释程序读取另一个程序的指令，按照规定改变被解释程序的状态。一个最小的解释循环可以写成：

```text
根据指令位置取出一条指令
辨认操作及其参数
执行规定的状态变化
决定下一条指令位置
重复，直到停机或报告错误
```

程序本身由“能直接执行的代码”变成了“另一段代码所读取的数据”。关键是定义清楚被解释机器的状态和每条指令的含义。

下面设计一台小型栈机器，支持 `PUSH`、`ADD`、`MUL`、`HALT`。它用 Python 整数，不模拟 MIX 的字宽、寄存器或溢出规则。

```python
def run_stack_program(program):
    stack = []
    trace = []
    ip = 0
    while ip < len(program):
        op, arg = program[ip]
        trace.append((ip, op, tuple(stack)))
        ip += 1

        if op == "PUSH":
            if type(arg) is not int:
                raise ValueError("PUSH 的参数必须是整数")
            stack.append(arg)
        elif op in ("ADD", "MUL"):
            if len(stack) < 2:
                raise ValueError("栈中操作数不足")
            right = stack.pop()
            left = stack.pop()
            stack.append(left + right if op == "ADD" else left * right)
        elif op == "HALT":
            if len(stack) != 1:
                raise ValueError("结束时必须恰有一个结果")
            return stack[0], trace
        else:
            raise ValueError("未知指令: " + str(op))
    raise ValueError("程序缺少 HALT")


program = [
    ("PUSH", 2), ("PUSH", 3), ("ADD", None),
    ("PUSH", 4), ("MUL", None), ("HALT", None),
]
answer, trace = run_stack_program(program)
print(answer)
print(trace[2])
```

输出为：

```text
20
(2, 'ADD', (2, 3))
```

它计算 $(2+3)\times4$。跟踪记录保存的是执行每条指令**之前**的栈快照。必须复制成 `tuple(stack)`；如果只保存同一个可变列表的引用，事后看到的就可能全部是最后状态。

这个小机器没有跳转，指令位置每次增加，所以对有限程序必然结束或报错。加入跳转以后，还需要讨论跳转目标、循环及调试时的执行步数限制。解释器自身的控制循环，不能自动保证任意被解释程序都终止。

## 5. MIX 模拟程序与跟踪程序

§1.4.3.1 给出 MIX 模拟程序的组织方式。模拟器至少需要表示内存、寄存器、符号、比较状态、溢出开关和被模拟的执行位置，并忠实实现各指令规则。

此时会同时存在两套时间：宿主程序实际花费的时间，以及被模拟 MIX 指令在模型中累计的时间。前者受模拟器实现影响，后者遵循目标机器的定义。不能用宿主 Python 的一次循环耗时直接充当 MIX 指令代价。

§1.4.3.2 进一步讨论跟踪程序。观察执行位置和寄存器变化，能够帮助定位第一次偏离预期的状态。原书还讨论如何让机器执行部分原始指令，同时让跟踪程序保留控制。

上面的 `trace` 只示范了记录执行前快照这一思想。追踪本身需要时间与空间；如果保存每一步的完整状态，数据量可能很大。实际阅读程序时，先选定要观察的变量和转移位置，往往比无差别打印所有内容更有效。

## 6. 输入输出：发起操作不等于数据已经就绪

在 MIX 模型中，`IN` 发起输入后，计算机还可以继续执行其他指令。读取目标内存前，必须确认传输已经完成；输出时也不能在设备仍使用缓冲区时随意覆盖它。

最直接的组织方式是发起 I/O，然后反复检查设备是否完成。原书接着讨论如何让计算与 I/O 重叠：当设备向缓冲区 B 读入下一块时，CPU 处理已经就绪的缓冲区 A；下轮再交换两者。

这里最重要的是缓冲区的使用权。某一块数据至少会经历：

```text
空闲 → 正在读入 → 已就绪 → 正在计算 → 空闲
```

计算只能读取已完成输入的数据，设备只能写入不再被计算使用的缓冲区。仅仅分配两个数组，而没有这些时序约束，并不能得到正确的双缓冲。

### 为什么重叠能缩短总时间

采用一个本文简化的模型：共有 $K\ge1$ 个块，每块输入耗时 $I$、计算耗时 $C$；只有一个输入设备和一个计算单元，两者能独立运行，忽略额外复制、同步和交换开销。

完全串行时，总时间为

$$
T_{\mathrm{serial}}=K(I+C).
$$

理想双缓冲需要先等待第一块输入，最后完成尾部计算；中间每推进一块受较慢阶段限制，所以

$$
T_{\mathrm{overlap}}=I+C+(K-1)\max(I,C).
$$

若 $K=4,I=5,C=3$，串行耗时 32，重叠耗时 23。具体时序为：

| 数据块 | 输入时间段 | 计算时间段 |
|---|---|---|
| 1 | 0—5 | 5—8 |
| 2 | 5—10 | 10—13 |
| 3 | 10—15 | 15—18 |
| 4 | 15—20 | 20—23 |

稳态下每块间隔是 5，输入成为瓶颈。这里的时间单位是任意一致单位，是模型计算结果，不是设备性能实测。

原书还比较了先复制数据再继续输入的方案与交换缓冲区的方案：如果复制处在关键路径上，复制成本不能忽略。更多缓冲区可以吸收阶段性的速率波动，也要付出存储和管理成本，并不能让一个已经饱和的输入设备无限加速。

## 7. 流程边界也是程序的一部分

流水线中间的重复过程容易画得很整齐，初始化和收尾却常被漏掉。实际设计至少要处理：第一块何时可用、最后不足一块的数据怎样计数、输入结束怎样传播、设备失败怎样报告，以及尚未完成的操作何时可以回收缓冲区。

前面的文本生成器就是一个小例子：如果忘记输入结束后的最后一次 `yield`，最后的 `-2` 会悄悄消失。算法主体正确，收尾条件遗漏，仍然会得到错误程序。

这也是原书从子程序逐渐讲到 I/O 的理由：每个局部过程都要对自己的入口、出口和状态转移负责，组合起来才有可靠的整体行为。

## 8. 历史和文献应该怎样读

§1.4.5 追溯这些技术的发展。书中提醒，许多基本技术由不同的人独立发展，历史并不总能压缩成“某个人在某年发明了某概念”。

阅读这部分时，可以把文献与具体机制对应起来：返回地址怎样保存，子程序库怎样形成，协程怎样交换恢复位置，解释程序如何在表达紧凑性、可移植性和执行开销之间取舍。

这些问题比单独记住年代更有助于阅读正文。对旧机器的细节，也应区分其实现背景与仍然存在的程序组织问题。
