# 【计算机程序设计艺术 TAOCP】卷1·2.5 动态存储分配：空闲总量够，为什么还会失败

> 对应原书：§2.5，第 409—428 页。本文按分配、释放、合并、比较的顺序整理，Python 代码是便于观察区间变化的教学模型。

前面用过的 `AVAIL` 表，大多管理大小相同的节点：申请时取出一个，释放时放回一个。现在把条件改掉——程序每次申请的大小可以不同，而且需要一段连续空间。

假如空闲区间的长度分别是 6、5、7，总共有 18 个空闲单元，申请 10 个连续单元却可能失败。每一块都太小，空闲总量无法回答这次请求。

这一节研究的就是：**怎样分割和重新合并空间，才能让后续申请继续得到满足？**

## 1. 先把三种空间成本分开

将存储池记作半开区间 $[0,C)$。长度为 $n$、起点为 $p$ 的块占据 $[p,p+n)$。

一个分配器至少需要维护块的大小、是否空闲，以及空闲块之间的查找关系。空间消耗有不同来源：

| 成本 | 发生在哪里 | 例子 |
|---|---|---|
| 管理信息 | 块头、块尾或独立管理表中 | 大小、状态、前后链接 |
| 内部碎片 | 已分配块内部 | 申请 9 个单元，却按大小类别分到 16 个 |
| 外部碎片 | 已分配块之间 | 空闲区总量充足，却没有足够长的连续区间 |

因此，比较方法时不能只统计“还有多少空闲空间”。至少还应观察最大空闲块、搜索成本，以及为了对齐或分类而额外分配的空间。

这里的“连续”针对当前讨论的地址空间；本文不把它直接等同于现代操作系统中的物理页连续性。

## 2. 首先适合与最好适合：名称没有给出胜负

原书从空闲块链表出发讨论两种选择：

- **首先适合（first fit）**：沿给定顺序，选择第一个足够大的块。
- **最好适合（best fit）**：选择足够大的块中最小的一个。

“首先”必须附带遍历顺序。按地址排序、按大小排序、从上次位置继续搜索，得到的过程可能不同。

“最好”的目标只是让**当前分配的剩余量最小**。后面还会请求什么，它并不知道。

看一个自拟例子：有长度 12 和 10 的两个空闲块，中间被占用块隔开；后续依次申请 8、9、4。首先适合按这两个块的地址顺序搜索。

| 请求后 | 首先适合的剩余块长度 | 最好适合的剩余块长度 |
|---|---|---|
| 申请 8 | 4、10 | 12、2 |
| 申请 9 | 4、1 | 3、2 |
| 申请 4 | 1，成功 | 最大只有 3，失败 |

这个例子足以否定“最好适合总能容纳更多请求”，却不能反过来证明首先适合永远更好。请求大小、释放顺序和空闲表的组织都会影响结果。

原书后面用相同请求序列做模拟比较，正是为了让不同方法面对同一份负载。书中基于 MIX 的计时结果，也应连同机器模型和实验分布一起理解。

## 3. 分割与释放，必须配套考虑

从长度 $s$ 的空闲块分配 $n$ 个单元，有两种直接情况：

- $s=n$：整块取走，空闲表少一个节点。
- $s>n$：切出所需部分，将剩余区间留在空闲表。

真实块格式还会规定最小可用块长度。如果余量小到放不下管理信息，就不能仍把它当作一个普通空闲块。可以整块交给申请者，并记录实际分配长度；这又会产生内部碎片。

释放时要检查地址相邻关系。对两个区间 $[a,a+s)$ 与 $[b,b+t)$，只有

$$
a+s=b
$$

时才能直接合并成 $[a,a+s+t)$。空闲链表上相邻，并不自动意味着地址上相邻。

把新释放的块记作 `X`，它有四种情况：左右都被占用；只有左边空闲；只有右边空闲；左右都空闲。最后一种情况要把三块合成一块，并从空闲表中移除原来的两个记录。

合并结束后，一个很好用的不变式是：**空闲表覆盖全部空闲单元，各块互不重叠，而且不再存在可直接合并的相邻空闲块。**

## 4. 一个能观察碎片的区间分配器

下面用 Python 列表保存按地址递增排列的 `(起点, 长度)`。它实现首先适合、最好适合和释放后合并。

模型把管理表放在池外，不计算块头、对齐、并发或操作系统开销；每个请求都恰好分配所需长度。返回值是模拟地址，地址 0 完全合法。

```python
from bisect import insort


class Arena:
    def __init__(self, capacity):
        if type(capacity) is not int or capacity <= 0:
            raise ValueError("capacity must be a positive integer")
        self.capacity = capacity
        self.free_blocks = [(0, capacity)]
        self.live = {}

    def allocate(self, size, policy="first"):
        if type(size) is not int or size <= 0:
            raise ValueError("size must be a positive integer")
        if policy not in ("first", "best"):
            raise ValueError("unknown policy")

        choice = None
        for i, (start, length) in enumerate(self.free_blocks):
            if length < size:
                continue
            if policy == "first":
                choice = i
                break
            if choice is None or length < self.free_blocks[choice][1]:
                choice = i

        if choice is None:
            raise MemoryError("no sufficiently large contiguous block")

        start, length = self.free_blocks[choice]
        if length == size:
            self.free_blocks.pop(choice)
        else:
            self.free_blocks[choice] = (start + size, length - size)
        self.live[start] = size
        return start

    def release(self, start):
        if type(start) is not int or start not in self.live:
            raise ValueError("not the start of a live allocation")
        size = self.live.pop(start)
        insort(self.free_blocks, (start, size))

        merged = []
        for p, n in self.free_blocks:
            if merged and merged[-1][0] + merged[-1][1] == p:
                q, m = merged[-1]
                merged[-1] = (q, m + n)
            else:
                merged.append((p, n))
        self.free_blocks = merged


pool = Arena(32)
a = pool.allocate(8)
b = pool.allocate(8)
c = pool.allocate(8)
pool.release(a)
pool.release(c)
print(pool.free_blocks)

try:
    pool.allocate(17)
except MemoryError:
    print("total free = 24, largest block = 16")

d = pool.allocate(12)
print(d, pool.free_blocks)
pool.release(b)
pool.release(d)
print(pool.free_blocks)
```

输出：

```text
[(0, 8), (16, 16)]
total free = 24, largest block = 16
16 [(0, 8), (28, 4)]
[(0, 32)]
```

申请 17 失败时，管理表没有发生变化。后面释放所有存活块，池重新合并成初始区间。

设空闲块数为 $f$。这个模型的分配与释放最坏都需 $O(f)$ 时间，释放还会建立一个 $O(f)$ 的合并列表。`insort` 虽然用二分查找插入位置，Python 列表的移动成本仍然是线性的。

`release` 只接受当前分配的起点，能拒绝内部地址和立即重复释放。不过地址可能被再次分配；保留旧地址后误用它，仍然可能碰到新的对象。这个模型没有代际编号，不能识别这种过期引用。

## 5. 边界标记：把邻居信息放到块的两端

按地址组织空闲表便于合并，但释放时仍可能需要搜索插入位置。原书的另一种办法是**边界标记**。

它在块的边界保留状态、大小等信息。对一个待释放块：

1. 向右加上本块长度，就能找到右邻块的边界。
2. 从左侧相邻位置读取左邻块的尾部信息，就能判断它是否空闲，并在需要时找到其起点。
3. 配合双向空闲链表，可以直接摘掉要参与合并的邻块。

这样，在书中块格式和合法输入的前提下，一次释放只需处理至多两个相邻块，合并部分可以在固定数量的操作内完成。存储池两端还需要合适的哨兵状态，防止越界。

这里省下的是“找物理邻居及摘链”的搜索；**不能据此宣布整个分配操作也变成了常数时间**。挑选足够大的空闲块仍取决于空闲表的组织方式。

## 6. 伙伴系统：用规则化尺寸换取容易查找的伙伴

伙伴系统把池的容量设为 $2^m$，块的长度限制为 $1,2,4,\ldots,2^m$。一个大块可以分成等长的两半，这两半互为伙伴。

申请时先向上取整到允许的块大小；没有合适的空闲块，就拆分更大的块。释放时，如果同级伙伴也空闲，就合并，并继续向上一层检查。

以池内从 0 开始的相对地址表示，长度为 $2^k$ 的块总是按 $2^k$ 对齐，其伙伴地址为

$$
\operatorname{buddy}_k(p)=p\mathbin{\mathrm{xor}}2^k.
$$

例如大小为 8 的块，起点 0 的伙伴是 8，起点 16 的伙伴是 24。但起点 8 与 16 的两个块虽然地址相邻，却不是同一对伙伴，不能直接按伙伴规则合并。

如果池的真实基址为 $B$，应对相对偏移做运算，再加回基址：`B + ((p - B) ^ size)`。还要确认伙伴处于同一池中、大小相同且确实空闲。

一次分割或合并最多经过 $m$ 层。是否能迅速摘掉某个伙伴，则需要相应的状态信息和链表操作支持。

代价也很明确：请求 9 个单元会占用大小 16 的块。这个差额属于内部碎片；伙伴系统也不保证所有地址相邻的空闲块都能立刻合并。

## 7. “百分之五十规则”说的是什么

原书分析了一种趋于均衡的分配与释放过程。设平均有 $N$ 个已分配块，每个存活块等可能成为下一个被释放者；设一次分配保留有效余块的概率为 $p$。在相应假设和忽略边界项的近似下，空闲块平均数 $M$ 满足

$$
M\approx\frac{pN}{2}.
$$

当 $p$ 接近 1，空闲块数大约是已分配块数的一半。这就是名称的由来。

这条结论**没有说“一半内存必然被浪费”**。块数与字节数不同，平均空闲块长度也未必等于平均已分配块长度。

推导的一个关键是按释放后的空闲块数变化分类：释放被两个空闲块夹住的块，空闲块数减一；只有一个空闲邻居时不变；没有空闲邻居时加一。再将平均释放变化与平均分配变化平衡起来。

如果释放顺序接近栈、对象寿命与位置相关，或者系统还没有进入均衡，等可能释放的假设就可能失效。单次快照不应被拿来验证一个均衡平均关系。

原书还讨论了利用已知请求分布安排不同大小槽位的“分布适合”。这一思路同样依赖分布和寿命假设：把负载信息用进算法，有可能减少浪费；假设失效时，原来的分析也就失去依据。

## 8. 回收、合并、紧凑：各自解决哪一步

| 过程 | 回答的问题 | 能否移动存活对象 |
|---|---|---|
| 可达性回收 | 哪些对象已经不需要保留 | 单靠判定不要求移动 |
| 空闲块合并 | 已空闲且地址相邻的块能否合成一块 | 不移动存活对象 |
| 紧凑 | 能否搬动存活对象，把空洞集中起来 | 需要移动，并修正引用 |

紧凑可以缓解外部碎片，但前提是系统能够找到并更新相关引用。如果程序把地址藏在无法识别的位置，移动以后就会留下错误指向。原书也讨论了复制到另一半空间的方法；这需要预留目标空间，并满足回收过程对引用的要求。

如果存活数据本身就超过容量，重新排列不会凭空创造空间。此时必须让调用者处理分配失败，或由更高层决定减少保留的数据、扩展空间、使用外部存储。

## 9. 读完后自己做一次比较

可以给上面的模型加一个事件表：每条记录包含申请大小、对象编号和释放时刻。让两种策略回放同一份事件，记录最大空闲块、失败位置与搜索次数。

不要只生成均匀随机大小。还可以试试固定大小、少量大块夹杂许多小块，以及严格后进先出的寿命。把造成差异的那一段区间画出来，比单独报一个平均耗时更容易解释结果。

本节最终留下的判断标准是：**分配策略要和块大小、寿命、地址约束以及允许付出的管理成本一起评价。**
